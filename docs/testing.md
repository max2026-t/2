# План тестирования

## Введение

Этот документ описывает стратегию тестирования проекта, включая виды тестов, подходы и ресурсы.

## Виды тестирования

*   **Unit-тесты.** Проверяют отдельные компоненты или функции. Требуемое покрытие кода: 80%.
*   **Integration-тесты.** Проверяют взаимодействие между компонентами.
*   **E2E-тесты (End-to-End).** Проверяют работу системы в реальных сценариях с участием пользователя.

## Подходы к тестированию

*   **Test-Driven Development (TDD).** Разработка ведётся параллельно с написанием тестов.
*   **Behavior-Driven Development (BDD).** Акцент на поведении системы (бизнес-цели), а не на реализации кода.

## Ресурсы

*   **`docs/api/`** — спецификация API.
*   **`docs/architecture/`** — архитектура проекта.
*   **`src/`** — исходный код проекта.

## Планы и сценарии

| Вид тестирования | Сценарий |
| :--- | :--- |
| **Unit-тест для сервиса UserService** | Проверка корректности создания, чтения и удаления пользователя. |
| **Integration-тест для API-эндпоинта /api/users** | Проверка корректности передачи параметров и валидации входных данных. |
| **E2E-тест для сценария оформления заказа** | Авторизация пользователя, добавление товара в корзину, расчёт стоимости доставки. |

## Критерии начала тестирования

*   **Unit-тесты:** покрыты 100% кода.
*   **Integration-тесты:** все сервисы подняты и доступны.
*   **E2E-тесты:** все бизнес-сценарии пройдены в staging-среде.

## Риски и ограничения

*   **Сложность мокинга внешних сервисов.** Может повлиять на покрытие интеграционных тестов.
*   **Нестабильность тестовых данных.** Некоторые тестовые сценарии зависят от актуальных данных в базе.

## Вывод

Данный план служит основой для организации тестирования. Дальнейшее развитие должно включать автоматизацию как можно большего числа тестов и покрытие edge-случаев.

## Рекомендации по обновлению

*   Архитектурные изменения должны сопровождаться обновлением соответствующих разделов в документации.
*   План тестирования следует актуализировать перед каждым крупным релизом.
